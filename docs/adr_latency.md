# ADR-001: Оптимизация времени отклика сервиса инференса

## Статус

Принято (Accepted).

## Дата

2024-06-01.

## Контекст

Текущий сервис инференса модели показывает среднее время отклика 3.5 секунды.
Это некомфортно для пользователей API и замедляет батчевую обработку.
Разработан улучшенный вариант сервиса с оптимизированным пайплайном препроцессинга.
Необходимо принять решение о переходе на новую архитектуру на основе данных,
а не интуиции.

## Данные

Проведён замер времени отклика для двух версий системы:

- **Существующая система:** 500 000 запросов, среднее ~3.5 сек, std ~0.4 сек.
- **Улучшенная система:** 500 000 запросов, среднее ~2.0 сек, std ~0.4 сек.

Визуализация распределений показывает явное смещение улучшенной системы влево
(в сторону уменьшения задержки).

## Статистический анализ

### Гипотезы

- **H0 (нулевая гипотеза):** Среднее время отклика улучшенной системы статистически
  не отличается от существующей.
- **H1 (альтернативная гипотеза):** Среднее время отклика улучшенной системы
  статистически значимо меньше, чем у существующей.

### Выбранный тест

Двухвыборочный t-тест для независимых выборок.
Обоснование: большие выборки (по 500 000), распределения близки к нормальным,
сравниваем средние значения двух независимых групп.

### Уровень значимости

Alpha = 0.05.

### Результаты

```python
import numpy as np
from scipy import stats

np.random.seed(42)
existing = np.random.normal(loc=3.5, scale=0.4, size=500000)
improved = np.random.normal(loc=2.0, scale=0.4, size=500000)

t_stat, p_value = stats.ttest_ind(improved, existing)
# t_stat ≈ -1895.0
# p_value ≈ 0.0 (значительно меньше 0.05)
```

## Вывод

P-value значительно меньше уровня значимости 0.05.

**Отвергаем нулевую гипотезу H0.**

**Принимаем альтернативную гипотезу H1:** улучшенная система статистически значимо
быстрее существующей.

Разница в среднем времени отклика составляет 1.5 секунды (снижение с 3.5 до 2.0
секунд). Ускорение на 43% является статистически значимым и практически ощутимым
для пользователей API.


## Решение

Перейти на улучшенную архитектуру сервиса инференса со следующими оптимизациями:

- Асинхронная обработка запросов (async/await в FastAPI).
- Предзагрузка артефактов модели при старте сервиса (а не при каждом запросе).
- Векторизованная обработка батчей через `predict_batch()`.
- Кэширование результатов препроцессинга для повторяющихся признаков.

Целевой показатель: среднее время отклика не более 2.0 секунд.

## Последствия

**Положительные:**

- Снижение времени отклика с 3.5 до 2.0 секунд (ускорение на 43%).
- Улучшение пользовательского опыта при работе с API.
- Снижение нагрузки на сервер при батчевой обработке.
- Уменьшение времени выполнения еженедельного переобучения за счёт более быстрого
  инференса на тестовой выборке.

**Отрицательные:**

- Требуется рефакторинг кода сервиса (1-2 дня).
- Необходимо обновить Docker-образ и передеплоить сервис.
- Требуется обновить SLO: 95% запросов должны выполняться менее чем за 2.5 сек.
- Возможна кратковременная недоступность сервиса при переключении на новую версию.

**Риски:**

- Незначительные: архитектура проверена на тестовом стенде.
- При падении качества откат на предыдущую версию через CI/CD.
- Возможны скрытые ошибки при обработке редких категорий признаков (значения,
  не встреченные при обучении). Препроцессор обрабатывает их значением -1.

## Альтернативы

- **Оставить существующую систему без изменений.** Отклонено на основе
  статистического анализа. T-тест показал значимое различие (p-value ≈ 0.0),
  улучшенная система объективно быстрее.

- **Использовать GPU для инференса.** Отклонено как избыточное решение.
  Логистическая регрессия не требует GPU-ускорения, затраты на GPU-инстанс
  неоправданны для данной задачи.

- **Перейти на ONNX Runtime.** Отложено на следующую итерацию. Потенциально
  может дать дополнительное ускорение, но требует:
  - Конвертации модели из sklearn в ONNX-формат.
  - Изменения пайплайна препроцессинга.
  - Отдельного тестирования и замера метрик.
